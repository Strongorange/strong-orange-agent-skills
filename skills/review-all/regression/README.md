# 회귀 하네스 — 렌즈를 고칠 때마다 돌려라

렌즈(각 SKILL.md의 게이트/목록)는 프롬프트다. 프롬프트를 고치면 **오탐이 늘거나 커버리지가 줄 수 있다.** 이 폴더가 그걸 즉시 잡는 A/B 테스트다.

## 구성

**렌즈 회귀** (지적 품질 — 상 픽스처 오탐 0, 하/중 recall)
- `fixtures/` — 도메인 **4종**(comment·test·solid·acid) × 수준(상/중/하) **14개** TS 파일. 상 수준엔 "지적하면 안 되는 함정"이 심겨 있음.

**오케스트레이터 회귀** (병합 품질 — 렌즈 회귀와 완전히 별개)
- `check-assignment.sh` — 1층. 파일→렌즈 배정과 acid 프리필터. **LLM 0개, 1초.**
- `merge-cases/*.json` — 2층. 녹화된 렌즈 출력. 병합 규칙만 검증(리뷰를 다시 시키지 않는다).
- `scenario/` — 3층. 5파일 골든 시나리오. 배정→fan-out→병합 전 경로 1회.

**정답지**
- `answer-keys/` — `ANSWER-KEY.md`(comment·test·solid) · `acid-ANSWER-KEY.md` · `merge-cases-KEY.md` · `scenario-KEY.md` · `scenario-assignment.txt`. **리뷰어 에이전트에게 절대 노출 금지.**

> **정답지 노출 방지 (절차로 막는다)**
> 정답지를 다른 폴더에 숨기는 걸로는 못 막는다 — 파일시스템 접근권이 있는 에이전트는 하네스 경로만 알면 한 칸 위를 볼 수 있다. 대신 **픽스처를 scratch 디렉토리로 복사해 그 경로만** 리뷰어에게 준다. 리뷰어는 하네스가 있다는 사실 자체를 몰라야 한다.
> ```bash
> cp regression/fixtures/comment-medium.ts "$SCRATCH/src/pricing.ts"   # 이 경로만 전달
> ```

## 채점 축

- **Recall**: 하/중 픽스처의 심은 결함을 잡나
- **오탐(FP)**: 상 픽스처의 "괜찮은 것"을 지적하나 ← 기계적 적용 지표
- **문서역행**: 원문이 금지한 지적("인터페이스 뽑아라" 등)을 하나 ← 핵심
- **Calibration**: overallLevel이 하<중<상으로 맞나

## 재검증 절차 — 뭘 고쳤냐에 따라 도는 범위가 다르다

| 고친 것 | 돌릴 것 |
|---|---|
| 렌즈의 게이트·지적 목록 | 렌즈 회귀(해당 도메인) |
| §1-1 배정표·프리필터 정규식 | 1층 (1초) |
| §3 병합·정렬·승격 규칙 | 1층 + 2층 |
| 그 외 구조 변경·릴리스 전 | 1층 + 2층 + 3층 |

### 렌즈 회귀 (fixtures)

1. 픽스처를 scratch로 복사해(위 박스) 그 경로를 리뷰어 서브에이전트에 준다. **맥락 0, 렌즈 파일만 Read시킴.**
2. 파일당 2~3명(FP는 희귀 이벤트라 표본 필요). 스키마: `{ overallLevel, primary[], other[] }`.
3. 회수 후 정답지와 대조. 상 픽스처 primary가 비고 하/중 결함을 잡으면 통과.

### 1층 — 배정·프리필터 (LLM 0개)

```bash
./check-assignment.sh --check     # PASS / FAIL + diff
```
프리필터 정규식은 `SKILL.md §1-1`과 이 스크립트 두 곳에 있다. **한쪽만 고치면 갈라진다.**

### 2층 — 병합 규칙 (에이전트 1개 × 5케이스)

리뷰를 다시 시키지 않는 게 핵심이다. 렌즈 출력은 이미 녹화돼 있고, 검증 대상은 병합 프롬프트뿐이다.

> review-all 스킬을 로드해 §3 병합·보고 규칙만 적용하라. 아래 JSON은 렌즈 fan-out 결과다(리뷰를 다시 하지 말 것). 규칙대로 최종 보고서를 출력하라.

케이스별 합격 조건은 `answer-keys/merge-cases-KEY.md`. 각 케이스가 고정하는 것:
`01` 렌즈 간 other 중복 제거 · `02` 도메인 밖 major 승격 · `03` 버킷 헤더 최저 레벨 · `04` 억지 지적 0 · `05` severity 정렬과 other 위치

### 3층 — 골든 시나리오 (전 경로 1회)

`scenario/` 디렉토리에 `/review-all`을 그대로 돌린다. 합격 조건은 `answer-keys/scenario-KEY.md`.
**에이전트 라벨 목록을 함께 확인할 것** — `acid:slugify.ts`가 뜨지 않았다는 건 보고서만 봐선 증명되지 않는다.

## 실측 baseline (이 렌즈들이 통과한 값)

- comment-good / solid-good / solid-good2 / test-good / acid-good / acid-good2: **primary 오탐 0**
- comment-medium: 0/2(맨몸) → **3/3**(렌즈)
- solid-medium: 0/2 → **2/2** (v1.1) · solid-bad 강신호 3/3
- test-bad 4/4 · test-medium 2/2
- acid-bad 4/4 · acid-medium 2/2. baseline이 overallLevel을 역전(bad=high)시킨 걸 렌즈가 교정(bad=low)
- 하드 함정("쪼개라/전략패턴/인터페이스"): **6명 전원 0**

## 오케스트레이터 baseline (2026-07-23 초회 실측)

- **1층**: PASS. 음성 케이스(clean 픽스처에 `prisma.slug.create` 한 줄 주입)에서 정상 FAIL — 통과만 하는 껍데기가 아님을 확인.
- **2층**: 5케이스 **5/5 PASS** (sonnet 1명씩). 렌즈 간 dedup·승격·최저레벨·억지지적 0·severity 정렬 전부 규칙대로.
  - 초회 실측에서 **규칙 공백 2건**이 드러나 그 자리에서 SKILL.md를 고침:
    1. 입력에 없는 렌즈 버킷 처리 규칙이 없어 출력이 3인 3색("대상 없음"/생략/"미실행"). → §3에 "안 돈 렌즈는 버킷 생략, '이상 없음'은 돌았는데 0건일 때만" 추가.
    2. 출력 형식 예시가 코드펜스 안에 있어 **보고서 전체를 펜스로 감싼 사례 1/5**. → 예시 아래 "펜스는 표기일 뿐" 명시.
  - 정답지도 1건 수정(04의 트랜잭션 버킷 조건이 틀렸음 — 입력에 없는 렌즈에 high를 요구했다).
- **3층**: 합격 조건 **7/7 PASS** (12 job, 렌즈별 sonnet 1명). 프리필터 미발화·배정·버킷 분리·dedup·승격·clean 표기·label.ts 함정 전원 통과.
  - 여기서도 규칙 공백 1건: **cross-bucket 중복**(acid가 primary로 잡은 사안을 comment·solid가 각자 `other`에 반복, severity도 불일치) → §3에 dedup ② + "담당 렌즈 severity 우선" 추가.
  - `slugify.ts` 픽스처에 실제 결함이 있어(연속·양끝 하이픈) 수정. 오탐 측정용 clean 픽스처는 진짜로 깨끗해야 한다.

## 알려진 한계

- 픽스처가 전부 **단일 파일 23~65줄**이라 교차 파일 신호(solid의 "여러 위치 중복"·"3곳 이상 복붙", acid의 "락 획득 순서 비일관")는 검증된 적이 없다. 오탐 0 주장의 적용 범위가 거기까지는 아니다.
- 2층은 케이스당 1명이라 저빈도 편차를 못 잡는다(펜스 사례가 1/5로 걸린 건 운). 규칙을 크게 고쳤을 땐 2~3명으로 늘릴 것.
- 렌즈 회귀·2·3층 모두 채점이 수동이다. 1층만 자동. 자주 고치게 되면 그때 스크립트화할 것.

## 알려진 교훈

- 렌즈의 "지적 금지" 목록이 고민감 상태에서도 함정을 막는 핵심. 신호를 추가할 땐 반드시 상 픽스처로 FP 회귀 확인.
- "값 객체 후보" 같은 광범위 신호는 good 코드에 노이즈를 유발 → "같은 검증 2곳 이상 반복"으로 하드 게이트할 것(v1→v1.1에서 이 이유로 수정).
