# 병합 규칙 정답지 (2층) — 에이전트 노출 금지

각 케이스는 `merge-cases/*.json`(녹화된 렌즈 출력)을 §3 병합 규칙대로 보고서로 만들게 하고, 아래 **합격 조건**을 사람이 대조한다. LLM 출력은 표현이 매번 달라지므로 바이트 일치가 아니라 조건 충족으로 채점한다.

리뷰어 프롬프트(정답지 언급 금지):

> review-all 스킬을 로드해 §3 병합·보고 규칙만 적용하라. 아래 JSON은 렌즈 fan-out 결과다(리뷰를 다시 하지 말 것). 규칙대로 최종 보고서를 출력하라.

---

## 01-dedup-other — 렌즈 간 `other` 중복 제거

- [ ] 기타 버킷에 `res.ok` 사안이 **1건만** 남는다 (3건 그대로 나열하면 실패)
- [ ] 줄번호가 42/44로 어긋나도 같은 사안으로 합쳤다
- [ ] 남은 서술이 셋 중 **가장 구체적인 것**(comment 렌즈의 "PG가 4xx/5xx를 반환하면 에러 본문을 승인 결과로 오인" 수준). "응답 상태 미검증"만 남으면 실패
- [ ] primary 3버킷은 전부 "이상 없음"
- [ ] **승격 줄(⚠)이 없다** — 최고 severity가 minor라 승격 대상이 아니다
- 흔한 실패: 같은 (파일, 줄)만 dedup하고 44는 별건으로 남기는 것

## 02-promote-other-major — 도메인 밖 major 승격

- [ ] 보고서 **맨 앞**에 `orderApi.ts:42` major 한 줄 요약이 있다
- [ ] 그러면서 기타 버킷에도 그대로 남아 있다 (맨 앞으로 옮기고 기타에서 지우면 실패)
- [ ] 주석·설계 버킷의 nit 2건은 승격되지 않고 제자리
- [ ] 정렬상 nit가 major 위로 올라가지 않는다
- 흔한 실패: `other`는 항상 아래라는 규칙만 보고 승격 줄을 빠뜨리는 것

## 03-overall-level-min — 버킷 헤더 레벨

- [ ] 설계 버킷 헤더가 **low** (clean.ts=high, messy.ts=low → 최저값). high면 실패
- [ ] 주석 버킷 헤더는 medium
- [ ] 테스트·트랜잭션 버킷은 입력이 없으므로 헤더 레벨 없이 "이상 없음" 또는 아예 생략 — 둘 다 허용
- [ ] `overallLevel`을 심각도로 오해해 "high=심각"으로 표기하지 않는다

## 04-all-clean — 억지 지적 0

- [ ] 주석·테스트·설계 버킷이 "이상 없음", 헤더 레벨 high
- [ ] **트랜잭션 버킷은 생략하거나 "미실행"으로 표기** — 입력에 acid 렌즈 결과가 아예 없으므로 "이상 없음 — high"로 쓰면 안 된다(안 돈 것과 돌아서 깨끗한 것은 다르다)
- [ ] 승격 줄 없음, 기타 버킷 비어 있음
- [ ] **입력에 없던 지적을 만들어내지 않는다** (파일명만 보고 "테스트가 부족해 보인다" 류 추측 = 실패)

## 05-severity-sort — 정렬과 버킷 순서

- [ ] 트랜잭션 버킷이 blocker(12) → major(33) → minor(55) → nit(70) 순
- [ ] 기타 버킷의 major(88)가 트랜잭션 버킷 **아래**에 온다 (severity가 같다고 primary와 섞으면 실패)
- [ ] 동시에 맨 앞 승격 줄에는 88이 올라온다 (기타에 major가 있으므로)
- [ ] 트랜잭션 버킷 헤더 low
