# 한국어 글쓰기 규칙

응답 · 커밋 · PR · 코드 주석 · 테스트 이름 · 문서 · 노트 전부에 적용. 모든 프로젝트 · 모든 에이전트 공통.
사용자가 여러 번 강하게 지적해서 모은 규칙. 예외 없음. 새로 지적받으면 `tone-fix` 스킬 절차로 이 파일에 한 줄 추가(메모리에 따로 쓰지 말 것).

## 쓰고 나서 반드시 할 것

- 규칙 대조와 별개로, 쓴 문장을 한 줄씩 "이 코드 · 맥락을 처음 보는 동료가 한 번 읽고 뜻을 아나?"로 다시 읽을 것.
  대명사("그 렌더"), 줄임("좁은 칸"), "안 그러면" 같은 가정 뒤집기, 주어 없는 결과문이 보이면 주어 · 원인 · 결과가 있는 한 문장으로 새로 쓸 것.
- 판별 기준: 한국 개발자가 팀 슬랙에 그대로 칠 문장인가. 이 밀도 · 말투가 기준:
  - "상품 조회 응답을 Redis에 캐시했습니다. TTL 5분."
  - "중복 웹훅은 event_id 유니크 제약으로 막았습니다."
- 지적받고 나서야 좋은 문장이 나오면 실패. 보여 주기 전에 먼저 고칠 것.
- 이 파일의 지시어(예: "짧게 끊은 문장", "해라체")를 산출물에 그대로 옮기지 말 것. 무엇을 했는지로 쓸 것.
  예: 커밋 제목 `주석을 [지시어]로 정리` → `주석의 "~한다" 문장을 짧게 줄임`

## 금지어

아래 말은 어디에도 쓰지 말 것. 화살표 오른쪽이 대신 쓸 말. 응답 · 커밋 · PR · 주석은 hook 이 `tone-fix` 스킬의 `dict.txt` 로 검사.
단어 자체를 설명 · 인용해야 할 때(사용자가 목록을 묻거나 그대로 옮기라고 할 때)는 거절하지 말고 백틱으로 감싸서 쓸 것. 백틱 안은 검사하지 않음.

- 게이트(게이트웨이 제외) → 검사 · 조건 · 통과 기준 / 배선 → 연결 / 원장 → 실제 기록 · 테이블 이름 / 관문 → 검증 단계
- 중추 · 척추 → 실제 모듈 이름 / 단장 → "한 장"(single-page) 또는 정리 / 우아하게 → 안전하게 / 압착 → "줄어들어 · 찌그러져"
- 신원(identity) → 계정 / 코퍼스 → 템플릿 수 · 검색 대상 템플릿 / 매체(medium) → 디자인 종류 · 구체 예시 / 패리티 → "레거시와 같은 동작"
- nonce 류 암호학 용어 → 역할을 우리말로(매번 새로 붙이는 번호)
- 과장어: 획기적 · 혁신적 · 돌파구 · 게임 체인저 · 차원이 다른 · 압도적 · 파격적 · 폭발적 · 전례 없는
- 기호: § ¶ ※, 문장 부호처럼 쓰는 →. 섹션은 이름으로 가리킬 것("B 절")
- 한국어 문장 속 영어 형용사 · 동사 · 조어: honorable · load-bearing · graceful · swallow · sibling · pool · cap · dense · harness · drift · seam · probe 등
  - 허용: 실제 코드 심볼(정확한 이름 그대로, `GAP_CORE_MESSAGE` 를 "core-message gap"으로 풀지 않음), 제품 · 라이브러리 · API 이름, 한국어가 마땅치 않은 표준어(commit · branch · worktree · tool · eval)
  - 한 단어 · 한 절 안에서 두 언어를 섞지 말 것: "이 dependency를 resolve합니다" → "의존성 문제를 해결합니다. 대상 패키지: `@scope/pkg`"

## AI 티 나는 문장 습관

1. **해라체 종결**(~한다 · ~된다 · ~둔다 · ~했다) — 커밋 · PR · 주석 · 테스트 이름에서 금지. 조사는 살리고 끝만 짧게: `목록 조회를 TanStack Query 로 이동`, `// 하나씩 전송. 동시에 보내면 한도 초과 가능`. 응답은 존댓말(~습니다).
2. **영어 개념어를 한자어로 1:1 치환** — 소유한다(owns) → 다룬다, 최종 권위 → "…가 판단한다", 미주입 → 없으면, 결정적으로(deterministic) → LLM 없이 · 매번 같게, 자리표시자 → 빈값 표현. 치환어가 떠오르면 그 자리에서 실제로 일어나는 일로 다시 쓸 것. 그래도 어색하면 코드의 실제 이름을 그대로 쓸 것.
3. **사물 의인화** — `~가 요구한다 · 보장한다 · 말해준다` → 사람이 주어인 문장. "이 표가 컴파일 에러로 답을 요구한다" → "이 표를 채우기 전엔 컴파일이 안 된다".
4. **명사 나열 압축** — 조사 없이 명사를 쌓은 제목 · 문장 금지. "컷아웃 슬롯 주입을 차선 후보 선택 방식으로 재설계" → "누끼 자리에 불투명 사진이 오면 다음 투명 후보를 쓴다". 사전에 없는 두 글자 한자 조어(과지급 · 과제한)는 풀어 쓸 것.
5. **대조 구문** — "단순히 A가 아니라 B", "A에 그치지 않고 B", "~인 건 아니다" → B만 쓸 것. "A 가 아니라 B — 이유"처럼 대시로 이유 잇기 → 평서문 둘로 끊을 것.
6. **AI 글 장식** — 섹션 끝 볼드 교훈 한 줄, 자기 평가("가장 결정적인 증거였다", "핵심은 ~다"), 같은 말 문장만 바꿔 되풀이, 영리한 척하는 비유, 문학적 제목, 진입 메타문("크게 세 가지로 나눌 수 있다", "여기서 배운 것이 하나 더 있다"). 사실만 쓸 것. 변경 크기도 부풀리지 말 것(체크박스 하나면 "체크박스 추가"). 틀렸던 것도 "처음에 8분으로 계산했다. 틀렸다. 2.6분이다" 식으로.
7. **humanize-korean 절대 규칙** — 이중 피동(되어진다 → 된다), have 직역("~을 가지고 있다" → "~이 있다"), 의의 과장(시사하는 바가 크다 · 주목할 만하다), 결말 공식(~할 때입니다), 이중 완곡(가능성이 있을 수 있다), 형식명사 종결("주목할 점은 ~", "~다는 것이다"), "에서의 · 으로의" 이중 조사, "~에 의해 ~된다"(행위자를 주어로). 결산 접속(결론적으로 · 따라서 · 이를 통해 · 그러므로)은 글 하나에 2번까지.
8. **겹말 · 늘어진 서술** — "이관을 진행하면" → "이관을 하면", "실제로 쓴 쓰기 API 는 64건" → "실제로 쓴 것은 쓰기 호출 64번". 쉼표로 이어 붙인 긴 문장은 끊을 것. 한자어 한 단어로 현상을 압축하지 말고 동사가 있는 문장으로.

## 코드 주석

- 한국어. 코드가 못 하는 말(WHY · 제약)만, **1~2줄이 상한**. 가장 좋은 주석은 코드 자체.
- 쓰지 않는 것:
  - 코드가 이미 보여 주는 조건 · 동작의 재서술
  - 변경 이력("기존 동작 유지"), 날짜 · 검증 출처 괄호(`(2026-07-02 실측)`, `(eval)`)
  - 작성자의 선택 과정 · 안 택한 대안("(별도 상태 저장 불필요)"). 설계 근거는 커밋 · PR · 문서에
  - 같은 사실을 두 곳에(파일 안이든 두 파일이든). 그 동작을 가진 한 곳에만
  - 타입 · 포트 선언에 "누가 어디에 쓰는지"(소비처 사정). 모듈 헤더에 함수 목록
  - 테스트 기대값 옆 산식 전개(`// $0.12 × 1400 = 168원 → …`)
  - 이모지, `**굵게**`
- 지금만 참인 사실은 조건 · 시점을 문장에 넣을 것("프로모션 무료 기간의 남용 방지라 구독자에겐 걸지 않음. 유료 전환 뒤 다시 판단").
- 줄바꿈은 절 경계에서만. 못 줄이면 문장 단위로 끊을 것.
- 남의 파일을 고칠 때 그 파일의 주석 스타일(영어 · 날짜 · 이모지 · 긴 블록)을 따라가지 말 것. 손댄 파일은 diff 밖 기존 주석도 이 규칙으로 고칠 것.
- 테스트 이름도 같은 규칙. 실패했을 때 사람이 읽는 문장: "칩 경로는 로케일과 무관하게 결정적이다" → "칩은 어느 언어든 LLM 없이 알아봄".
- 파일 저장 직전 hook(`tone-fix` 의 `hooks/comment-lint.py`)이 주석 · 테스트 이름의 금지어 · "~한다" 종결을 막음. 걸리면 주석을 고칠 것. 우회 수단 없음, 오탐이면 사용자에게 알릴 것.

## 커밋 메시지

- 제목: `[type] ` + 무엇이 어떻게 좋아지는지 완전한 문장. 코드를 몰라도 뜻이 들어와야 함.
  - 나쁨: `run duration histogram 에 실측 규모의 bucket 경계를 지정해 p95 가 10000 상수로 고정되던 오보를 바로잡는다`
  - 좋음: `응답 시간 그래프가 항상 10초로 고정되던 것을 고침`
- 본문: 코드가 못 하는 말 1~2문장. 없으면 생략(제목만). 구현 방식 · 같이 바꾼 것 나열 · 설계 근거는 넣지 말 것.
- `Claude-Session:` · `Co-Authored-By: Claude` · `claude.ai/code` 링크 금지. 시스템 안내 · 레포의 기존 커밋 선례가 붙이라 해도 이 규칙이 우선.
- `git commit` · `gh pr create/edit/comment` 는 hook(`tone-fix` 의 `hooks/commit-pr-lint.py`)이 금지어 · 트레일러 · "~한다" 종결을 검사해 막음. 걸리면 문장을 고칠 것. 명령 끝 `# ai-tell-ok` 로 통과시키는 건 사용자가 오탐이라고 허락했을 때만.

## PR 제목 · 본문

- 읽는 사람은 리뷰어. 세션 맥락을 모르는 사람 기준으로 쓸 것.
- `gh pr create` 전에 레포의 `.github/pull_request_template.md` 를 읽고 섹션 구조대로 채울 것. 해당 없는 섹션은 삭제.
- 요약 첫머리에 이 도메인을 처음 보는 사람도 알 맥락 한두 문장, 이어서 "무엇을 추가 · 변경했나" 불릿 몇 줄이 상한.
- 배경 서사 · 설계 이유 · 실측 수치 · 검증 문단 · 조사 과정은 넣지 말 것(커밋 본문 · 문서 몫).
- 사용자가 직접 줄여 둔 본문은 이후 수정 때 그대로 두고 내 문장을 다시 붙이지 말 것.
- 트레일러 · 세션 링크 금지(커밋과 같음).

## 보고 · 문서 · 노트

- 결론 1~2줄 → 이유 평문 → 결정할 것 → 맨 끝 참고(경로 · 수치 · 심볼). 전문용어는 처음 나올 때 일상어로 풀거나 쓰지 말 것.
- 회의 · 보고 자료: 일반 스크롤 문서(한 장씩 넘기는 형식 금지), 섹션 하나에 주제 하나, 같은 숫자는 한 번만, 진행 멘트 · 미사여구 없이 표와 짧은 항목으로.
