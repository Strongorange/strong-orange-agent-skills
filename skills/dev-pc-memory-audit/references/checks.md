# 점검 항목

항목마다 "이런 모양이면 → 이렇게 줄임 → 이걸 확인"으로 씀. 특정 에이전트 · 도구 이름은 맨 끝 "사례"에만 있음. 대상 PC 에 깔린 에이전트 · 도구의 공식 문서와 실제 설정 파일을 읽고 같은 패턴을 찾을 것.

## 1. 세션 수만큼 복제되는 보조 프로세스

모양: 에이전트 · 에디터 세션 하나를 띄울 때마다 같은 종류의 자식 프로세스(도구 서버, 언어 서버, 래퍼)가 하나씩 더 뜸. 세션 수 × 종류 수로 늘어서, 세션을 많이 띄우는 사람에게 가장 큼.

줄이는 법(위에서부터 시도):
1. **안 쓰는 것은 기본에서 뺌.** 가끔 쓰는 것은 별도 설정으로 옮겨 필요할 때만 붙임. 그 에이전트가 설정 파일을 추가로 읽는 옵션이나 프로필 기능이 있는지 문서에서 찾음.
2. **원격 서비스를 로컬 래퍼로 감싸고 있으면 직접 연결.** 클라이언트가 원격 전송 방식(HTTP · SSE 등)을 직접 지원하는지 확인. 클라이언트마다 지원 범위가 다르니 각각 확인.
3. **서버가 네트워크 실행을 지원하면 공용 서버 하나로.** `--help` · 소스에서 transport · port 옵션을 찾음. OS 서비스 관리자(systemd · launchd · 작업 스케줄러)로 상시 실행하고 `127.0.0.1` 에만 엶. 세션들은 주소로 붙음.
4. **런처(`npx` · `uvx` · `uv run` · `bunx` 류)로 띄우면 설치 후 실행 파일을 직접 실행.** 런처 프로세스가 서버마다 하나씩 더 붙음. 자동 업데이트가 사라지니 주기 작업으로 업데이트를 돌림.
5. **인증만 붙여 넘기는 로컬 중계는 클라이언트의 동적 헤더 기능으로.** 헤더를 명령으로 만들어 주는 기능이 있고, 인증 실패 때 그 명령을 다시 실행하는지 확인. 만료 시간보다 긴 간격으로 두 번 호출해서 이어지는지 볼 것.
6. **네트워크 실행이 없어도 상태가 없는 서버면** 범용 stdio → HTTP 프록시로 공용화할 수 있음. 가끔 쓰는 것이면 1번이 더 간단.

공용으로 두면 안 되는 것: 실행한 폴더 · 프로젝트에 묶인 것(언어 서버, 프로젝트 dev 서버에 붙는 도구), 세션별 상태를 들고 있는 것(열린 브라우저 탭 등). 서버가 세션별 상태를 따로 나눠 주는 옵션이 있으면 예외.

확인할 것:
- 공용 서버가 오래 살면서 붙잡는 상태: 연결 풀의 트랜잭션 · 스냅숏, 캐시, 로그인 세션. 원래 세션과 함께 꺼지던 것이 이제 며칠씩 남음. 연결 · 트랜잭션 처리 코드를 읽을 것.
- 공용 서버가 죽으면 모든 세션이 같이 잃음. 자동 재시작을 걸 것.
- 등록을 누가 관리하는지. 팀 · 회사 스크립트가 업데이트 때 다시 등록하면 지워도 돌아옴. 그 스크립트가 등록 여부를 무엇으로 판단하는지 읽고, 이 PC 에서만 끌 수 없으면 팀원 기본 동작은 그대로인 옵트인 옵션이나 끄기 파일을 팀에 제안.
- 설정 파일에 적혀 있다고 실제로 뜨는 것은 아님. 에이전트가 그 파일 · 그 키를 실제로 읽는지 프로세스 목록과 에이전트의 상태 명령으로 확인한 뒤 절감액에 넣을 것.
- 떠 있는 세션은 시작할 때 읽은 설정으로 계속 돎. 오래된 세션을 pid · 실행 시간으로 짚어 재시작 대상으로 보고.

## 2. 언어 서버 · 코드 인덱서

모양: 에이전트나 에디터가 띄운 언어 서버가 큰 저장소 · worktree 마다 수백 MB ~ 수 GB. worktree 를 여러 개 열면 그만큼 늘어남.

줄이는 법:
- 같은 언어의 더 가벼운 구현(네이티브 포트, 새 메이저 버전의 LSP)이 있으면 바꿈. 클라이언트의 언어 서버 설정을 직접 고치면 업데이트 때 덮일 수 있으니, 사용자 쪽 설정 · 로컬 플러그인처럼 업데이트가 건드리지 않는 곳에서 바꿈. 새 버전은 전용 폴더에 설치해 전역 도구 버전을 건드리지 않음.
- 거의 안 쓰는 언어의 서버는 끔. 끄면 에이전트는 검색 · 파일 읽기로 대신함.

확인할 것: 바꾼 뒤 새 세션에서 정의 이동 · hover 같은 호출 한 번. 프레임워크가 언어 서버 플러그인에 기대는 기능(예: 타입 생성 · 경고)이 빠지는지.

## 3. 에디터

- 언어 서버는 2번과 같은 방식.
- 안 쓰는 AI · 확장 기능은 끔. 일부 상주 프로세스는 끌 설정이 없을 수 있음.
- 파일 감시 제외 목록에 빌드 산출물 폴더를 넣기 전에, 에디터 타입 정보가 그 폴더에 기대는지 확인(패키지 타입을 빌드 산출물에서 읽는 모노레포, 프레임워크가 생성하는 타입 폴더). 기대면 넣지 말 것.
- 사용자가 정해 둔 메모리 상한은 묻기 전에 바꾸지 말 것.

## 4. 가상 머신 · 컨테이너 런타임 (WSL · Docker Desktop · VM)

모양: 호스트에서 VM 프로세스(`vmmemWSL` · `vmmem` 등)가 VM 안의 실제 사용량보다 훨씬 큼. 대개 VM 안의 파일 캐시를 호스트에 안 돌려줘서 생김.

줄이는 법:
- VM 이 제공하는 회수 옵션을 확인하되, 동작 조건(유휴 상태에서만 등)을 문서에서 읽고 실제로 줄어드는지 잼.
- 안 되면 VM 안에서 주기적으로 캐시를 비움(Linux 는 `sync; echo 1 > /proc/sys/vm/drop_caches`, 시스템 timer). root 가 필요하면 명령을 사용자에게 줌.
- VM 메모리 상한은 주 작업 환경이면 낮추지 말 것. 낮추기 전에 물음.

## 5. 데스크톱 앱 · 자동 시작

- 자동 시작 목록에서 중복 등록 · 지운 앱의 잔재를 정리. 지우기 전에 목록을 백업.
- "필요할 때만 켜는" 앱은 자동 시작만 끔. 늘 쓰는 앱은 크더라도 그대로.
- 내장 브라우저 엔진(WebView2 · Electron 류)을 쓰는 앱은 프로세스 이름만으론 주인을 모름. 부모를 따라가 주인 앱별로 합쳐 보고.
- OS 기능 중 웹 결과 · 추천을 불러오는 것(시작 메뉴 웹 검색 등)은 끌 수 있으면 끔. 정책 위치는 관리자 권한이 필요할 수 있으니 명령을 사용자에게 줌. 파일 · 앱 검색은 살림.
- 사용자가 꺼도 재부팅 뒤 다시 켜지는 상주 프로세스가 있음. 다음 점검 때 다시 확인.

## 6. 오래 켜 두는 직접 만든 · 관리하는 앱

모양: 트레이 앱 · 백그라운드 도구가 "원래 이렇게 안 컸다".

줄이는 법(앱 코드를 고칠 수 있을 때):
- 큰 파일을 통째로 읽지 않고 줄 단위 · 스트리밍으로 읽고, 이미 읽은 위치부터 이어 읽음.
- 무거운 일회성 작업은 자식 프로세스에서 돌리고 결과만 받음. 끝나면 메모리가 통째로 돌아옴.
- GC 런타임은 큰 작업 뒤 메모리 반환(압축 GC 등)과 런타임의 메모리 절약 설정을 확인.
- 측정 → 설계 → 단계별 구현 → 같은 측정으로 재확인. 할당량 예산 테스트를 남겨 회귀를 잡음.

## 7. 디스크 (메모리와 같이 정리할 때)

- 컨테이너 런타임: build cache · 안 쓰는 이미지 · 볼륨 정리(남길 볼륨은 물음). 가상 디스크 파일은 따로 압축해야 공간이 돌아오는 경우가 많음.
- 지운 도구의 잔재: 홈의 설정 · 캐시 폴더, 앱 데이터 폴더, 시작 메뉴, URL 스킴 등록. API 키 같은 비밀 파일은 지우기 전에 물음.
- 측정용 파일 · 임시로 깐 도구 · 빌드 산출물은 끝나면 지움. 산출물은 배포본이 남아 있는지 대조한 뒤.

## 공용 로컬 서버 보안 점검

세션별 stdio 는 띄운 클라이언트만 말을 걸 수 있었지만, 공용 서버는 이 PC 의 다른 프로그램도 요청할 수 있음. 직접 요청해서 확인:
- LAN IP 로 접근 → 연결 안 돼야 함(`127.0.0.1` 바인딩)
- 위조한 `Host` 헤더 → 거부(DNS rebinding)
- 외부 Origin 의 CORS preflight · preflight 없는 단순 요청(`text/plain`) → 거부
- 세션 · 인증 없이 도구 호출 → 거부
- VM 의 `127.0.0.1` 이 호스트로 전달되는지(WSL 은 기본 전달됨). 접속 정보가 이미 같은 사용자 권한 파일에 있었다면 노출 범위는 이전과 같음. 접속 정보는 600 권한 파일로 옮김.
- 읽기 전용이어도 운영 데이터면 읽기만으로 개인정보가 나갈 수 있음. 기준은 "누가 읽을 수 있나". 서버 로그에 쿼리 파라미터가 남는지도 확인.

## 사례 (Windows + WSL, Claude Code · Codex 세션 4~6개, 한 번 측정)

숫자는 이 PC 의 1회 관찰. 대상 PC 에서 다시 잴 것.

| 항목 | 전 | 후 | 쓴 방법 |
|---|---|---|---|
| 세션마다 뜨는 MCP(세션 5개) | 약 7GB | 수백 MB | 1번의 1 · 2 · 3 · 4 · 5 |
| Python DB MCP 2종 × 세션 6개 | 1.5GB | 0.25GB(공용 서버 2개) | 1번의 3. 읽기 전용 모드가 autocommit 을 꺼서 스냅숏이 고정되던 문제를 같이 고침 |
| 인증 중계 MCP 2종 × 세션 4개 | 619MB | 0 | 1번의 5(Claude Code `headersHelper`, 401 때 재실행) |
| 에이전트 TypeScript LSP(큰 모노레포) | 2.3GB | 0.3GB | 2번(TS 7 `tsc --lsp` 로컬 플러그인) |
| 에디터 TS 서버(같은 파일) | 1.17GB | 0.44GB | 3번(TS 7 Native Preview) |
| vmmemWSL | 19.6GB | 12.4GB | 4번(1시간 drop_caches timer) |
| .NET 트레이 앱 | 1.6GB | 0.1GB | 6번 전부 |

이 사례에서 겪은 함정:
- Claude Code 는 `~/.claude/settings.json` 의 `mcpServers` 를 읽지 않음. 팀 스크립트가 거기 등록한 서버는 원래 안 떴음.
- `claude mcp get` 출력에는 `headersHelper` 가 안 나와서, 등록을 확인하는 스크립트가 직접 연결 등록을 못 알아봄.
- Codex 는 SSE 원격 서버를 직접 못 붙어 래퍼가 남음.
- WSL 에서 `systemctl --user` 가 bus 오류로 실패함(WSLg 가 `/run/user/<uid>` 를 덮음). 서비스 파일과 `default.target.wants` 링크를 직접 만들면 재부팅 때 적용됨.
