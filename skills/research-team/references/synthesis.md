# 종합 절차 (메인)

조사원 보고가 다 들어오면 메인이 아래 순서로 `synthesis.md` 를 씁니다. 별도 평가자 에이전트는 두지 않습니다. 사용자 맥락을 가장 많이 아는 쪽이 메인이고, 앞선 두 조사 모두 이 방식으로 조사원 오류를 잡았습니다.

## 1. 결론을 바꿀 주장 고르기

- 보고 전체에서 "이게 틀리면 결론이 바뀌는" 주장을 10~15건 뽑습니다. 후보 순위, 단가, 라이선스, 지원 범위, 중단 예정, 품질 비교 근거가 주로 해당합니다.
- `[주장]` `[2차]` `[논문→유추]` 태그가 붙은 것과 조사원끼리 서로 다르게 적은 것을 우선.

## 2. 원문 재확인

- 고른 주장마다 조사원이 적은 URL 을 직접 엽니다(WebFetch · agent-browser · context7). 조사원의 요약을 믿지 않고 원문 문장을 봅니다.
- 결과를 세 가지로 적습니다: 확인됨(`[문서 확인]` 으로 승격) / 틀림(바로잡은 내용) / 못 열었음(`[미확인]` 유지, 이유).
- 실례: 가상 착용 모델 조사에서 "가방 · 신발 지원 미확인" 은 공식 문서에 지원으로 적혀 있었고, "첫 공개 2026-06" 은 버전 API 로 2026-04-17 이었습니다.

## 3. synthesis.md 구성

1. **결론** 3~5줄. 각 줄에 태그.
2. **후보 표** — 조사원 표를 합치고 태그 통일. 기준 후보 대비 칸 유지.
3. **첫 실측 후보** 표 — 순위 · 무엇을 · 입력 · 반복 · 볼 것 · 이 순서인 이유. 실측은 다음 단계라 여기선 설계만.
4. **뺀 것** — 한 줄 이유 + 태그.
5. **조사원 보고 중 바로잡은 것** — 누가 무엇을 어떻게 틀렸고 원문은 뭐라 했는지. 다음 조사의 페르소나 · 렌즈 개선 입력이 됩니다.
6. **조사원 간 모순** — 같은 항목에 다른 값이 나온 것과 원문 재확인 결과. 원문으로 안 풀리면 여기서만 보강 조사원 1명을 띄웁니다.
7. **미확인 목록** — 못 연 것, 계정이 없어 못 본 것, 실측해야 아는 것. 사용자 결정이 필요한 것(키 발급 등)은 따로 표시.
8. **출처 URL** — 재확인한 것은 "(직접 확인)" 표시.

## 4. 사용자 보고

결론 → 후보 표 → 뺀 것 → 바로잡은 것 → 미확인 · 다음 단계. 수치 · URL 은 표와 맨 끝 참고에만. 기획 · 가격 · UX 제안은 넣지 않습니다. 실측 착수는 사용자 지시 뒤.

## 5. 되먹임

바로잡은 것 · 모순에서 반복되는 유형이 보이면 `lenses.md` 의 해당 절이나 `personas.md` 의 반대 근거 담당 질문에 한 줄 추가합니다. 메모리에 따로 쓰지 않습니다.
