# 공통 브리프 — <주제> (<YYYY-MM-DD>)

조사원 전원 필독. 칸은 전부 채웁니다. 모르는 칸은 "없음 · 미정"으로 적고 비워 두지 않습니다.

## 무엇을 정하려는가
이번 조사의 산출물이 무엇에 쓰이는지 한 문단. 예: "어떤 후보를 실측으로 돌릴지와 그 실측을 어떻게 평가할지". 조사 뒤에 누가 무엇을 하는지(실측은 메인이 함 등).

## 대상 · 제품 맥락 (사실만)
- 기능 · 입력 · 출력이 지금 어디까지 정해져 있는지. 정해지지 않은 것은 "미정"이라고 쓰고 두 해석 모두 다루게 합니다.
- 정본이 되는 파일 · 화면 · 문서 경로(읽는 방법 포함. 브랜치에 있으면 `git show origin/<branch>:<path>`).
- 지금까지 고른 후보가 있으면 이름 · URL · 고른 시점.

## 판정 기준 (중요도 순)
1. …
2. …
후보 표의 칸과 1:1 로 대응시킵니다.

## 운영 환경 · 자원
- 서버 스택 · 언어 · GPU 유무.
- 쓸 수 있는 계정 · 키(있는 것만). 없는 벤더는 "사용자 결정 필요".
- 상업 서비스 여부와 라이선스 기준(비상업은 "성립해도 못 씀"으로 표시).

## 이미 아는 사실 (다시 조사할 필요 없음, 반박하려면 근거 필요)
- 선행 프로젝트 실측 결과 · 교훈(수치 · 날짜 포함).
- 이미 확인한 단가 · 스키마 · 약관과 그 확인 방법(예: Replicate 단가는 페이지 HTML 의 `billingConfig` JSON).
- 이미 뺀 후보와 이유.

## 조사 규칙
1. 공식 문서 · 모델 카드 · 가격표 · 라이선스 · 논문 원문을 먼저 읽고 결론을 씁니다. 블로그 · 커뮤니티는 보조. **모든 주장에 URL.**
2. 확인 수준 태그: `[문서 확인]` `[2차]` `[주장]` `[논문→유추]` `[실측 필요]` `[추정]`. 모르는 칸은 "미확인".
3. 라이선스 · 상업 이용 가능 여부를 모델 · 가중치 · 학습 데이터 · 라이브러리 전부에 적습니다.
4. 날짜를 적습니다: 공개일 · 최신 버전 · 실행 수 · 중단 예정일.
5. 유료 호출 · 서비스 가입 · 얼굴 등 민감 데이터 내려받기 금지. 코드 실행은 설치 가능 확인까지만.
6. 파일 · 노트 · 브랜치를 고치지 않습니다. 결과는 지정된 파일 하나에만.
7. 기획 · 가격 · UX 제안을 하지 않습니다.
8. JS 렌더 페이지는 `agent-browser`(세션 이름 = 담당 이름). 라이브러리 문서는 context7 우선.
9. 보고는 한국어 합니다체. 결론 1~2줄 → 후보 표 → 제외 목록(이유 한 줄) → 미확인 목록 → 출처 URL.
